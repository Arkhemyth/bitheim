# v0.2.0 Delivery Plan — Managed Regtest Node

## Status

Active

## Purpose

This document is the execution-level source of truth for the `v0.2.0` milestone. It refines the milestone defined in [`docs/plan_bitheim.md`](../plan_bitheim.md) into reviewable vertical increments without replacing the project-wide plan, accepted specifications, or Architecture Decision Records (ADRs).

Operational progress is summarized in [`docs/PROJECT_STATUS.md`](../PROJECT_STATUS.md), which points contributors to the currently active phase and its governing documents.

## Milestone Objective

Deliver a reproducible and secure managed Bitcoin Core `regtest` experience through which two users can start nodes, connect them, create wallets, obtain test funds, execute a valid transaction, and observe its progression through the mempool and into a block.

Bitcoin Core remains the final authority for blockchain, transaction, script, wallet, UTXO, proof-of-work, and peer validation. Bitheim manages, coordinates, queries, and presents these operations without reimplementing Bitcoin consensus or wallet validation.

## Milestone Acceptance

The milestone is complete when a documented end-to-end scenario demonstrates that two independently configured users can:

1. start reproducible Bitcoin Core nodes in `regtest`;
2. verify node health and blockchain identity;
3. connect the nodes as peers;
4. create or load local wallets without exporting private key material;
5. generate and mature regtest funds;
6. send a valid transaction from one wallet to the other;
7. observe the transaction in the mempool and confirm it in a mined block; and
8. inspect the essential workflow through human-readable and JSON CLI output, with a deliberately basic TUI for the supported views.

The complete quality suite and the real two-node end-to-end validation must pass on the supported development and CI environment before release.

## Scope

### Included

- managed Bitcoin Core lifecycle for `regtest`;
- explicit separation of Bitheim state, Bitcoin blockchain data, and wallet data;
- secure local RPC cookie authentication;
- node health and blockchain status;
- wallet creation, loading, addresses, balances, and UTXOs needed by the milestone workflow;
- regtest block generation and coinbase maturity handling;
- human-originated transactions;
- block, mempool, and peer observation;
- human-readable and JSON CLI output;
- a basic TUI over existing application services;
- reproducible two-node integration and end-to-end tests.

### Excluded

- `mainnet`, `testnet`, or real funds;
- the custom `labnet-v1` Bitcoin Core fork;
- synthetic activity and experiment orchestration;
- analytical persistence, DuckDB, CSV, or Parquet;
- external proof-of-work mining;
- remote multi-user authentication;
- automatic Headscale or Tailscale administration;
- a native managed Bitcoin Core runtime, provisionally deferred until after `v1.0.0`;
- a complete production TUI or every view described for `v1.0.0`;
- premature asynchronous execution, caching, or performance tuning without measurements.

## Delivery Principles

1. Deliver each phase as a narrow vertical increment with an independently reviewable specification and acceptance criteria.
2. Introduce domain models, application ports, and infrastructure adapters only when exercised by a real use case. Do not create empty packages or speculative interfaces for symmetry.
3. Domain code must not import Bitcoin Core, Docker, operating-system process APIs, transport clients, or presentation frameworks.
4. Application services define the ports they require; infrastructure adapters implement those ports; CLI and TUI invoke application services rather than adapters directly.
5. Bitcoin Core validation results must be preserved and translated into safe, typed Bitheim errors rather than duplicated or overridden.
6. Security-sensitive operations must fail closed and must not expose cookies, authorization headers, private keys, seeds, raw configuration, personal paths, or unsanitized RPC payloads in logs or errors.
7. Documentation and project status are part of the deliverable whenever an increment changes the active phase or operational contract.
8. Runtime boundaries remain portable enough for a possible post-`v1.0.0` native adapter, but no native-runtime code or speculative selection framework is introduced before a real consumer exists.

### Phase 1 — Runtime Contract and Architecture

Define before implementation:

- the exact Bitcoin Core version and verifiable distribution source;
- the process/container boundary between Bitheim and Bitcoin Core;
- the Docker Compose topology and supported local execution contract;
- ownership, permissions, mounting, creation, and cleanup rules for each data directory;
- lifecycle semantics for start, stop, status, startup timeout, shutdown timeout, partial failure, and recovery;
- regtest ports, network isolation, peer addressing, and collision handling;
- RPC cookie discovery, access control, lifetime, and redaction rules;
- compatibility checks and the future Bitcoin Core upgrade policy;
- the minimum real domain model, application ports, and adapters required by Phase 2.

Expected documents:

- [`SPEC-0004: Managed Regtest Node Runtime Contract`](../specs/SPEC-0004-managed-regtest-node-runtime.md) (Accepted);
- [`ADR-0005: Docker Compose Runtime Topology`](../adr/ADR-0005-docker-compose-runtime-topology.md) (Accepted);
- an additional ADR only if selecting or distributing Bitcoin Core requires a distinct long-lived architectural decision.

Phase exit: the documents are independently reviewed, contain testable acceptance criteria, and leave no security-critical runtime choice implicit.

### Phase 2 — Managed Node Lifecycle and Health

- provide a reproducible single-node `regtest` deployment;
- extend `bitheim doctor` to report actionable Docker Engine and Compose prerequisite failures before lifecycle mutation;
- create only the explicitly authorized runtime directories with restrictive permissions;
- implement `start`, `stop`, and `status` application use cases and CLI commands;
- distinguish stopped, starting, unhealthy, incompatible, and healthy states;
- model only the node status and health concepts required by these use cases;
- introduce the first real process-control port and infrastructure adapter;
- preserve idempotent behavior where operationally safe and provide actionable failures otherwise.

Phase exit: a clean environment can start one node, identify its health and network, stop it gracefully, and repeat the workflow without manual repair.

### Phase 3A — Secure RPC and Read-Only Observation (Core)

- read the local RPC cookie only at the adapter boundary and only when required;
- use explicit connection and request timeouts;
- translate transport, authentication, protocol, and Bitcoin Core RPC failures into typed safe errors;
- validate JSON-RPC response shapes before constructing typed DTOs;
- expose node and chain overview (version, chain identity);
- add human-readable and deterministic JSON CLI output modes;
- extend `doctor` with read-only Bitcoin Core diagnostics without turning it into a lifecycle command;
- test that credentials and unsafe payloads never appear in output or structured logs.

Phase exit: Bitheim can securely inspect a running node while tests demonstrate protocol validation, timeout behavior, redaction, and deterministic JSON output.

### Phase 3B — Secure RPC and Read-Only Observation (Extended)

Phase 3B is delivered as two contract-first vertical increments. The split isolates block lookup and shared-deadline complexity from the distinct monetary-precision and peer-privacy risks without introducing layer-only pull requests.
Together, these increments preserve the accepted block, mempool, and peer observation boundary.

#### Phase 3B.1 — Block Inspection

- add an immutable typed block summary and unambiguous hash-or-height locator contract;
- validate lowercase block hashes, non-negative heights, counts, sizes, timestamps, weight, and optional adjacent hashes;
- use `getblockhash` for height lookup and `getblock` with verbosity `1` without exposing raw transaction bodies;
- preserve one caller-owned monotonic deadline across a two-request height lookup;
- map unknown hashes and heights to a typed safe resource-not-found failure;
- expose concise human output and deterministic JSON through `bitheim inspect block`;
- delegate through the existing unprivileged Compose boundary without starting dependencies; and
- verify the behavior against the pinned Bitcoin Core 31.1 regtest image.

Increment exit: block lookup by hash and height satisfies the accepted bounds, deadline, privacy, error, CLI, and real-integration contracts while all historical and protected tests remain intact.

#### Phase 3B.2 — Mempool and Peer Observation

Phase 3B.2 uses two complete contract-first cycles rather than one broad implementation handoff. Phase 3B.2a delivers mempool observation first; Phase 3B.2b then delivers peer observation. Each cycle integrates its protected contracts before implementation and receives an independent review before the next cycle begins.

##### Phase 3B.2a — Mempool Observation

- add an immutable typed mempool summary;
- convert Bitcoin fee values exactly to integer satoshis without binary floating-point arithmetic and reject negative, non-finite, or sub-satoshi precision;
- expose deterministic human and JSON forms through `bitheim inspect mempool`;
- preserve read-only, no-auto-start Compose delegation and real Bitcoin Core integration coverage.

Increment exit: mempool observation satisfies the accepted precision, validation, privacy, CLI, delegation, and real-integration contracts while all historical and protected tests remain intact.

##### Phase 3B.2b — Peer Observation

- add immutable typed peer summaries;
- omit the deprecated `startingheight` field and represent unknown synced heights as optional values;
- enforce the 256-entry peer bound and all field-level validation required by SPEC-0005;
- expose peer endpoints only in explicitly requested output and prohibit them from logs, unrelated diagnostics, and errors;
- expose deterministic human and JSON forms through `bitheim inspect peers`;
- preserve read-only, no-auto-start Compose delegation and real Bitcoin Core integration coverage; and
- reconcile project status and mark Phase 3 complete after independent review and integration.

Phase exit: Bitheim supports all four Phase 3 read-only observation use cases with typed structured output, safe failures, real integration coverage, and no runtime mutation.

### Phase 4 — Wallet and Regtest Funds

Phase 4 is governed by [`SPEC-0006: Wallet and Regtest Funds`](../specs/SPEC-0006-wallet-and-regtest-funds.md) and uses three complete contract-first cycles. The split keeps wallet lifecycle, monetary observation, and state-changing block generation independently reviewable without creating layer-only pull requests.

#### Phase 4A — Wallet Lifecycle and Receiving Address

- create an explicitly configured local descriptor wallet through Bitcoin Core;
- load an existing wallet with safe already-loaded behavior;
- validate a conservative wallet identity and use explicit wallet-scoped RPC endpoints;
- obtain a native SegWit receiving address;
- preserve the stopped-node, no-auto-start, deadline, cookie, and privacy boundaries; and
- expose deterministic human and JSON CLI output.

Increment exit: a user can create or load a wallet and obtain a receiving address through the delegated container boundary while protected lifecycle, endpoint, malformed-response, and leak contracts pass against real Bitcoin Core 31.1.

#### Phase 4B — Balance and UTXO Observation

- represent every monetary value as an exact integer number of satoshis inside the domain;
- expose trusted, untrusted-pending, and immature wallet balances without combining their meanings;
- expose only the bounded UTXO fields required by the milestone workflow;
- order UTXOs deterministically and reject malformed or over-limit collections;
- avoid inferring coinbase identity from `listunspent`; and
- keep wallet names, addresses, transaction IDs, scripts, descriptors, and financial facts out of logs and unrestricted errors.

Increment exit: a user can inspect exact empty and funded wallet balances and bounded spendable UTXOs through human and JSON output with real Bitcoin Core 31.1 coverage.

#### Phase 4C — Regtest Block Generation and Maturity

- verify exact Bitcoin Core version and `regtest` identity before mutation;
- generate from 1 through 1,000 blocks to an explicitly supplied address;
- validate the exact bounded block-hash result under one monotonic deadline;
- communicate the difference between the 100-block maturity interval and the initial 101-confirmation funding workflow;
- demonstrate the authoritative immature-to-trusted balance transition; and
- provide the verified wallet-and-regtest-funds user guide.

Increment exit: a user can generate and mature test funds safely, then inspect the resulting spendable balance without Bitheim reading wallet files or accessing private key material.

Phase exit: a user can create a wallet, obtain an address, generate and mature test funds, and inspect the resulting spendable balance.

### Phase 5 — Transactions and Two-Node Networking

- connect and inspect two regtest peers;
- send a human-originated wallet transaction through Bitcoin Core;
- observe the transaction in the receiving workflow and mempool;
- mine a confirming block and inspect confirmations and final balances;
- expose actionable errors for insufficient funds, immature coinbase, unreachable peers, rejected transactions, and incompatible network identity;
- automate the milestone's real two-node transaction path.

Phase exit: the end-to-end transaction portion of the milestone acceptance passes reproducibly without accessing or exporting private keys.

### Phase 6 — Basic TUI and Milestone Validation

- provide only the node overview, blockchain status, wallet balance, simple transaction, mempool, and peer views required by the milestone;
- consume the same application services used by the CLI;
- work without color, support small terminals, document shortcuts, and confirm destructive actions;
- finalize user and operator documentation;
- define and verify the official immutable Bitheim application image distribution contract for isolated wheel installs (registry/source, version tag plus digest/pinning, acquisition behavior, and development override) before tagging `v0.2.0` (Phase 2 currently fails closed when the image is absent and no checkout build context exists);
- run the full quality, security, integration, container, and two-user end-to-end gates;
- reconcile project status and release documentation before tagging `v0.2.0`.

Phase exit: all milestone acceptance criteria are met and no planned `v0.2.0` behavior exists only as an untested presentation-layer shortcut.

## Modern Python Engineering Standard

The existing Python 3.13, Ruff, strict MyPy, Pytest, `uv`, and `src-layout` baseline remains mandatory. During `v0.2.0`, contributors should apply the following practices when they improve the actual design:

- prefer composition and explicit dependency injection over inheritance and service locators;
- use `Protocol` for genuine application ports where structural typing improves substitution and tests;
- use frozen, slotted dataclasses for small immutable value objects when identity and mutation are not required;
- use enums for closed state sets and specific exception types for meaningful failure categories;
- use context managers for resources with a real acquisition and release lifecycle;
- use `pathlib`, timezone-aware timestamps, integer satoshis, and `Decimal` only where decimal representation is genuinely required;
- validate untrusted JSON before conversion to typed DTOs and avoid `Any` or unbounded string-keyed mappings crossing architectural boundaries;
- make side effects and dependencies explicit, keep return types predictable, and avoid ambiguous boolean parameters;
- document public contracts and non-obvious invariants without adding ceremonial docstrings to trivial internals;
- follow the applicable PEP 8, PEP 257, PEP 440, PEP 484, and PEP 621 conventions already established by the master plan.

Practices associated with *Fluent Python* are adopted selectively: effective use of the data model, protocols, iterables, context managers, immutability, and composition is encouraged when supported by a concrete use case. Advanced abstractions are not goals by themselves.

The accepted hexagonal architecture is Bitheim's application of clean architectural boundaries. A second overlapping layer taxonomy must not be introduced merely to claim compliance with a named methodology.

## Performance Policy

Optimization follows evidence:

1. establish correct and secure behavior;
2. make the behavior observable and testable;
3. measure representative workloads with profiling or benchmarks;
4. optimize a demonstrated bottleneck while preserving tests and clarity.

The initial workload is predominantly local process and RPC I/O. Implementations should begin synchronously with explicit timeouts and bounded operations. `asyncio`, parallelism, caching, pooling, native extensions, or micro-optimizations require a measured need or a documented operational constraint.

## Verification Strategy

Every implementation phase must include the applicable subset of:

- pure unit tests for domain behavior and application services using explicit fakes;
- contract tests for each infrastructure port and JSON-RPC translation boundary;
- integration tests against the pinned Bitcoin Core version;
- functional tests for human-readable and JSON CLI behavior;
- security tests for RPC cookie handling, authentication, filesystem permissions, errors, and structured-log redaction;
- container tests on the supported architectures where runtime topology changes;
- an automated two-node end-to-end test before milestone completion;
- Ruff formatting and linting, strict MyPy over `src` and `tests`, Pytest, and repository diff checks.

Code coverage should become visible during this milestone. Its first introduction may be informational so the project can establish a meaningful baseline; a blocking threshold requires evidence that it will discourage untested behavior without rewarding low-value tests.

## Principal Risks

| Risk | Required Mitigation |
| --- | --- |
| RPC cookie or authorization leakage | Restrictive filesystem access, adapter-local credential handling, safe errors, categorical logs, and explicit leak tests. |
| Destructive datadir behavior | Explicit directory ownership and lifecycle contract; no implicit deletion or broad recursive operations. |
| Bitcoin Core version drift | Pin and verify the supported version; test compatibility and fail clearly on unsupported versions. |
| Domain coupling to RPC or Compose | Define ports from application needs and keep protocol/process details inside infrastructure adapters. |
| Flaky integration tests | Use deterministic regtest setup, bounded readiness checks, isolated resources, and diagnostic artifacts that contain no secrets. |
| Overextended TUI scope | Implement only views needed for milestone acceptance and reuse existing application services. |
| Premature abstraction or optimization | Require a current consumer, test, measurement, or documented architectural constraint. |

## Decisions Pending in Phase 1

- the supported Bitcoin Core version and immutable verification mechanism;
- whether the initial supported runtime is exclusively Compose-managed or also supports an externally managed local node;
- the precise container image source and trust/pinning policy for Bitcoin Core;
- datadir volume layout, ownership, backup boundary, and teardown semantics;
- local RPC exposure and cookie-sharing mechanism between containers;
- port allocation and peer discovery for multiple local or remote participants;
- readiness and health criteria, including timeouts and compatible node versions;
- where integration and end-to-end tests run when container execution is unavailable.

These decisions must be resolved by reviewed specifications or ADRs before lifecycle implementation begins. They must not be silently chosen inside an adapter or Compose file.

## Progress Maintenance

When a phase is integrated:

1. mark it `Completed` in the delivery table;
2. mark the next phase `In progress` only when its planning or implementation actually begins;
3. update [`docs/PROJECT_STATUS.md`](../PROJECT_STATUS.md) with the active phase, increment, governing documents, and next action;
4. preserve completed phase descriptions as historical delivery context; and
5. keep specifications and ADRs authoritative for their respective contracts and decisions rather than duplicating them here.
